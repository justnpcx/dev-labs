触发场景

按难度分了四级：初级建立直觉 → 中级学会用工具 → 高级理解实现 → 终极直面生产事故。建议顺着往上走，别跳级。
红框按钮会真的把对应资源打爆 —— 都在容器内，有 cgroup 硬限制兜底，不会影响宿主。
鼠标停在按钮上可以看这个场景对应的核心代码（ⓘ 标记）。
堆 OOM 之后所有请求都会失败（堆满了），点右上角「复位」即可恢复。
死锁无法靠复位解除，需要 ./lab.sh restart。
GC 空转需要先 ./lab.sh restart gc-overhead 换 profile 才可能触发报错， 当前默认 G1 下只会一直空转不报错。
线程池 / 锁竞争 / JIT / 连接池 这些场景也都能用 ./lab.sh trigger <名字> 触发， 完整清单见 ./lab.sh trigger help。

注意：每次堆快照约 235MB，会自动写到宿主磁盘，记得定期 ./lab.sh clean。
清空：活跃日志（gc.log / app.log）会被截断而不是删除 —— 它们正被 JVM 的 -Xlog 和 logback 持有，删了的话写入方会继续往那个 「已经看不见的 inode」里写，空间不释放、面板永远空着。其余文件直接删除。 怎么判断"被持有"是扫 /proc/self/fd，不是维护一份白名单。

Arthas 线上排错 （靶子在 /demo/*）

Arthas 已打进镜像（/opt/arthas），不需要下载。 它解决的是"日志不够用、又不能重启加日志"这个问题 —— 直接看运行中 JVM 的方法调用、耗时、入参出参，还能改线上代码。 靶子 /demo/order 里埋了四处问题，下面是挖出来的方法。

① 排错定位

总耗时 300ms，但慢在哪一层？日志里没有。

./lab.sh arthas-demo
用 trace 看逐层耗时 —— 实测 quotePrice 一层吃掉 99.9%。
用 watch 看方法入参出参，不用加一行日志、不用重启。

② 性能瓶颈

知道慢，但不知道是谁在烧 CPU。

./lab.sh arthas "profiler start"
火焰图上 SimpleDateFormat.<init> 会非常显眼 —— 那是"每次调用都 new 一个"的代价。代码 review 时看不出来，火焰图上藏不住。

③ 紧急热更新

改一个字符，但走发版流程要等几小时。

./lab.sh arthas-hotfix
jad → 改 → mc → retransform，不重启让新代码生效。
实测 VIP 折扣 90 → 80。改动只在内存里，restart 即还原。
进交互式控制台：./lab.sh arthas　　完整步骤：./lab.sh arthas-demo　　 出问题重置：./lab.sh arthas-reset
两个容器加固带来的坑（都已在 lab 里绕开，但值得知道）：
· Arthas 的 agent 驻留在目标 JVM 里，启动参数第一次就定死了 —— 改了配置要 arthas-reset 才能生效
· Docker 的 tmpfs 默认带 noexec，async-profiler 是 native 库需要 mmap 成可执行段，会报 failed to map segment from shared object。 本 lab 单开了一个带 exec 的 /arthas-tmp 给它用
