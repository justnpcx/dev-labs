## 界面速览

顶栏从左到右：标题 / 连接状态 / 运行时长 / **主题切换** / 复位 / 刷新。

主题支持**浅色 / 深色 / 跟随系统**三态，默认跟随系统。

下面依次是：

1. **KPI 行** —— 堆 / 元空间 / 堆外直接内存 / 线程，四张等高的卡，各带一条实时曲线
2. **GC + 隔离边界** 两栏 —— 前者看 GC 次数与停顿，后者是从容器内读的 cgroup 真实限制

4. **Arthas 线上排错** —— 三个场景（排错定位 / 性能瓶颈 / 热更新）的入口与说明
4. **日志与快照** —— GC 日志 / 应用日志 / 线程栈 / 堆快照
5. **输出** —— 每次触发接口的原始 JSON 返回
6. **实际生效的 JVM 参数** —— `RuntimeMXBean.getInputArguments()` 的返回值

## 1. 通用操作循环

每个场景都是这 4 步：

```
① 记基线  →  ② 点按钮  →  ③ 看「输出」面板 JSON + 左侧指标曲线  →  ④ 点「复位」
```

要盯的四个地方：

| 位置 | 看什么 |
|---|---|
| 左侧**指标曲线** | 趋势。哪条线在动、动多少 |
| 底部**输出面板** | 这次的 JSON 结果，含 `errorType` / 耗时 |
| 顶部**告警条** | 变红说明堆/元空间 >85%，或有死锁 |
| **日志与快照面板** | 事后取证，看堆栈、GC 日志、下载快照 |

> ⚠️ **「复位」在右上角。做完每个场景都点一下。**
> 不复位的话堆一直是满的，后续所有请求都会失败——这不是 bug，是堆真的满了。

### ★ 悬停看核心代码

**「触发场景」面板里每个按钮，鼠标停上去会浮出这个场景对应的核心代码。**

带 `ⓘ` 标记的按钮都有提示（12 个场景按钮 + 右上角复位 + 2 个快照按钮）。
提示里包含三部分：

```
┌─────────────────────────────────────────────┐
│ OomController.java  heap()      ← 代码出处   │
├─────────────────────────────────────────────┤
│ for (int i = 0; i < count; i++) {           │
│     byte[] block = new byte[mb*1024*1024];  │
│     LeakRegistry.holdBytes(block);  ← ★高亮 │
│ }                                           │
├─────────────────────────────────────────────┤
│ BYTE_BUCKETS 是 static 的，对象永远可达 →    │
│ GC 一个都收不走。        ← 为什么会导致问题   │
└─────────────────────────────────────────────┘
```

代码是从真实源码摘的（`src/main/java/lab/jvm/`），`★` 标的是**导致问题的关键那一行**。

**推荐用法**：点按钮之前先停一下看代码，猜一下会发生什么，再点。
点完对着「输出」面板和曲线验证自己的猜测 —— 这个来回比单纯看现象有效得多。

几个特别值得对着看的：

| 按钮 | 看什么 |
|---|---|
| 堆 OOM vs 慢速占堆 | **同一段代码，只是参数不同** —— 理解"分配"和"泄漏"的区别 |
| 元空间 OOM | `holdClass(clazz)` —— 持有 Class 就等于持有 ClassLoader |
| 直接内存 OOM | `holdDirect(buffer)` —— 堆外内存靠 Cleaner，强引用在就还不了 |
| CPU 打满 vs 停止空转 | 一个是 `while(!isInterrupted())`，一个是 `t.interrupt()` —— 配对的 |
| 复位 | `ClassFactory.reset()` —— 为什么只清 List 不够 |

## 3. 逐场景步骤

### 第一组 · 热身

#### 3.1 慢速占堆

| | |
|---|---|
| 按钮 | **慢速占堆** |
| 参数 | 4MB × 5 = 20MB |
| 耗时 | < 1 秒 |

**操作**：连点 **3~5 次**。

**观察**：
- 堆 `usedMb` 走 13 → 33 → 53 → 73，曲线出现明显台阶
- 输出面板 `"outcome": "no OOM"`

**收尾**：复位 → 堆掉回 12MB 左右。

**教学点**：这是"正常分配"。**没有泄漏时复位后堆会回落** —— 记住这个对照，后面看泄漏才有基准。

---

#### 3.2 渐进泄漏 +2MB×5

| | |
|---|---|
| 按钮 | **渐进泄漏 +2MB×5** |
| 参数 | 每次 +10MB，写进静态缓存**永不淘汰** |
| 耗时 | < 1 秒 |

**操作**：连点 **5 次**。

**观察**：
- 堆从 13MB 涨到 ~63MB，**曲线形态和慢速占堆一模一样**
- 区别在输出面板的 `staticCacheEntries`：5 → 25，**只增不减**

**收尾**：复位。

**教学点**：单看曲线分不出"正常分配"和"泄漏"。真正的区别是**长期趋势** ——
真实泄漏是放几天一直涨。在这个页面上只能靠连点模拟，真正的定位要靠第 5 节的快照对比。

---

### 第二组 · 内存类 OOM（三种，强烈建议连着做）

这一组是全场最重要的对比实验。**三种 OOM 分别在三个不同的内存区域**，
连着做才能建立"到底是哪块内存"的直觉。

#### 3.3 堆 OOM

| | |
|---|---|
| 按钮 | **堆 OOM** |
| 参数 | 8MB × 64 = 512MB（堆上限 256MB） |
| 耗时 | 1~3 秒 |

**观察**：
- 堆曲线**冲到 ~200MB 然后断崖**（OOM 后对象被清）
- 顶部告警条变红：`堆使用率 96%，即将 OOM`
- 输出面板：`"errorType": "Java heap space"`，`allocatedMb` ≈ 208

**副作用**：`dumps/` 里可能出现 `java_pid1.hprof`，**约 235MB**。
**但只在本次 JVM 生命周期内第一次触发时才有** —— 详见下面「堆快照的三个反直觉行为」。

**收尾**：复位 → 堆回落到 12MB。

**深入**：日志与快照 → 点 `logs/app.log` → 看到完整堆栈（`OutOfMemoryError` 那行标红）。

---

#### 3.4 元空间 OOM

| | |
|---|---|
| 按钮 | **元空间 OOM** |
| 参数 | 动态生成 20 万个类（上限 128MB） |
| 耗时 | **10~25 秒**，期间页面会卡住，**别刷新** |

**观察**：
- **元空间曲线从 37MB 爬到 128MB**（这条线平时几乎不动）
- **堆和直接内存几乎不变** ← 重点
- 输出面板：`"errorType": "Metaspace"`，`generatedClasses` ≈ 88000

**收尾**：复位 → **等 1~2 秒**再看，元空间回落到 37MB。

> 为什么要等：类卸载发生在 Full GC 期间，而 Full GC 是并发的。
> 不等的话你会以为"复位没生效"。

**教学点**：元空间不在堆里。**做一次 heap dump 你会发现里面根本找不到这 88000 个类** ——
这是排查 OOM 时最容易走错的路。

---

#### 3.5 直接内存 OOM

| | |
|---|---|
| 按钮 | **直接内存 OOM** |
| 参数 | 16MB × 64 = 1024MB（上限 64MB） |
| 耗时 | 1~2 秒 |

**观察**：
- **「堆外直接内存」从 0 冲到 64MB**
- **堆几乎不动** ← 又一个"不在堆里"
- 输出面板：`"errorType": "Direct buffer memory"`，消息里带 `limit: 67108864`

**收尾**：复位。

**教学点**：`-Xmx` 管不到它，只受 `-XX:MaxDirectMemorySize` 约束。
这是 Netty / NIO 类应用 OOM 的典型形态 —— **堆看着很健康，进程内存却一直在涨**。

---

### 第三组 · 资源类（不是内存不够，是资源上限）

#### 3.6 线程数 OOM

| | |
|---|---|
| 按钮 | **线程数 OOM** |
| 参数 | 建 400 个线程（容器 `pids.max = 320`） |
| 耗时 | 1~3 秒 |

**观察**：
- **线程数从 23 飙到 ~290**
- 输出面板：`"errorType": "unable to create new native thread"`，`createdThreads` ≈ 282

**收尾**：**必须点复位** —— 那 282 个线程在 sleep 300 秒，复位会 interrupt 它们。
不复位的话线程数会一直挂着。

**教学点**：报的是"内存"错误（`OutOfMemoryError`），但根因**不是堆**，
是进程数上限 + 每个线程的栈（`-Xss512k`）。
真实环境里这个限制来自容器编排平台或 `ulimit -u`。

---

#### 3.7 CPU 打满

| | |
|---|---|
| 按钮 | **CPU 打满** |
| 参数 | 2 个空转线程（容器配额 2 核） |
| 耗时 | 立即返回 |

**观察**：
- **页面上看不到 CPU** ← 这个场景的观察点在页面之外
- 另开终端：`docker stats jvm-lab` → CPU 冲到 ~200%

**收尾**：点「**停止空转**」。

**深入**：配合 `./lab.sh diagnose` 做，看 `jstack` 里 `lab-cpu-spin-*` 线程
状态是 `RUNNABLE` 且 `cpu=` 数值很大。

**教学点**：CPU 100% 的定位链路是 `top -H` 拿线程号 → 转 16 进制 →
`jstack` 里按 `nid` 找。容器里没有 `top`，这条路要用 `jcmd Thread.print` 代替。

### 第四组 · 并发类

#### 3.8 栈溢出

| | |
|---|---|
| 按钮 | **栈溢出** |
| 耗时 | < 1 秒 |

**观察**：输出面板 `"depthReached" ≈ 2553`。

**收尾**：无需复位（没占内存）。

**教学点**：`-Xss512k` → 约 2553 层。想对比就把 `-Xss` 改大再看这个数字怎么变。

---

#### 3.9 死锁

| | |
|---|---|
| 按钮 | **死锁** |
| 耗时 | ~1 秒 |

**观察**：
- **顶部告警条变红**：`检测到 2 个死锁线程（复位无效，需 ./lab.sh restart）`
- **线程面板「死锁线程」变成 2**（红色）
- 输出面板给了 jstack 命令

**收尾**：⚠️ **点复位没用！** 必须 `./lab.sh restart`。

**教学点**：`reset` 只能清引用、打断线程，**改不了已经形成的锁等待环**。
这也是死锁在线上特别讨厌的原因 —— 重启往往是唯一的解。

### 第五组 · GC 空转

#### 3.10 GC 空转

**⚠️ 界面做不到这一步**：这个场景**必须先换 JVM 参数**，而界面改不了参数。

**前置（终端）**：

```bash
cd /data/ai-stack/dev-labs/jvm-lab
./lab.sh restart gc-overhead     # 切成 Serial GC + -Xmn4m
./lab.sh limits                  # 确认 GC 真的换过去了
```

**然后**点「**GC 空转**」按钮。

**观察**：
- GC 面板的 `Pause Young` 次数**暴涨**（几十秒内上千次）
- **当前配置下不会报错** —— 输出面板显示 `no OOM`

**深入（重点）**：
1. 日志与快照 → 点 `logs/gc.log`
2. 勾上「**自动刷新（2 秒）**」
3. 看 `Pause Young` 行**刷屏**，每行都是 `239M->238M(255M)` —— **每次只回收 1MB**

**教学点**：这就是"GC 空转"。G1 **不抛** `GC overhead limit exceeded`
（它压根没实现这个检查），只会无限空转、请求越来越慢、日志里什么错都没有。
**这才是线上真实发生的事。**

做完记得切回来：`./lab.sh restart default`

## 4. 「日志与快照」面板怎么用

事后取证的地方。做任何一个 OOM 场景后都值得看一眼。

| 操作 | 说明 |
|---|---|
| **刷新列表** | 重新扫描 `logs/` 和 `dumps/` |
| **采集线程栈** | ★ 采 3 次、间隔 2 秒，写入 `logs/threaddump-*.txt`，采完自动打开 |
| **生成堆快照（live）** | ★ 推荐。先做一次 Full GC 只留存活对象，文件更小更聚焦。有短暂停顿 |
| **生成堆快照（含垃圾）** | 包含未回收的垃圾对象，文件更大，但保留现场 |
| **点左侧文件名** | 查看内容。GC 日志的 `Pause` 行、线程栈的死锁段都会自动上色 |
| **自动刷新** | 勾上后每 2 秒重读当前文件 —— 看 GC 日志必备 |
| **下载** | 选中 `.hprof` 后出现，拿到本地用 MAT 打开 |

### 线程栈怎么看（三种颜色）

点开一个 `threaddump-*.txt`，页面上会这样上色：

| 颜色 | 内容 | 含义 |
|---|---|---|
| 🔵 **蓝色** | `"thread-name" #25 daemon prio=5 ... nid=0x2a` | 线程头。快速扫有哪些线程 |
| 🔴 **红色** | `java.lang.Thread.State: BLOCKED`、`Found one Java-level deadlock` | 锁竞争 / 死锁，最该看的 |
| 🟡 **黄色** | `- waiting to lock <0x...>`、`parking to wait for` | 在等某把锁 / 在 park |

**关键用法 —— 三次采样法**：

「采集线程栈」默认采 **3 次、间隔 2 秒**，不是偷懒，是**必须**。
单次 dump 只能告诉你"此刻在哪"，看不出"卡住没动"。正确的判读方式是：

```
在文件里搜同一个线程名，比较 3 次采样的栈：
  · 栈完全一样  →  真的卡住了 ★ 这就是你要找的
  · 栈在变化    →  它在正常干活，别管它
```

摘要里会自动给你三样东西，先看摘要再决定要不要翻文件：

```json
{
  "deadlockedThreadCount": 2,
  "deadlockedThreads": ["lab-deadlock-A", "lab-deadlock-B"],
  "threadCount": 31,
  "stateDistribution": { "RUNNABLE": 14, "BLOCKED": 2, "WAITING": 11 },
  "topThreadNames": { "lab-cpu-spin": 2, "http-nio-8080-exec": 10 }
}
```

| 摘要字段 | 怎么用 |
|---|---|
| `deadlockedThreadCount` | > 0 就是死锁，`deadlockedThreads` 直接告诉你是哪几个线程 |
| `stateDistribution` | 大量 `BLOCKED` → 锁竞争；`WAITING` 多通常是线程池空闲，正常 |
| `topThreadNames` | 同名线程堆积（如 `lab-cpu-spin: 2`）就是问题所在 |

#### ⚠ `deadlockedThreadCount` 数的是**线程**，不是**死锁环**

实测对比：

```
jcmd 文本：  Found ONE Java-level deadlock        ← 数的是环
摘要字段：   "deadlockedThreadCount": 2           ← 数的是线程
```

一个环通常涉及 2 个线程，所以这两个数字天然不一样。**别拿它们互相对照**，
看到对不上就以为哪里出错了。

#### 重复点「死锁」按钮只会得到 1 个环

`LOCK_A` / `LOCK_B` 是 **static** 的。第一次形成的环永久占住这两把锁，
之后再触发的新线程只能在**链条**上排队等，形不成新环。

实测（连点 3 次后）：

```
#35 lab-deadlock-A  持有 68e0，等 68d0  ┐
#36 lab-deadlock-B  持有 68d0，等 68e0  ┘ ← 唯一的环，jcmd 报的就是这个
#37 lab-deadlock-A  等 68e0 ← 被 #35 占着，永远等不到（链，不是环）
#38 lab-deadlock-B  等 68d0 ← 被 #36 占着
#39/#40 同理

jcmd 里能看到 6 个 lab-deadlock 线程，但 findDeadlockedThreads() 只返回 2 个。
```

这其实是个好例子：**「BLOCKED 的线程数」和「死锁线程数」是两回事**。
排查线上问题时，如果只看 BLOCKED 的数量，很容易把大面积的锁排队误判成死锁。

> `deadlockedThreadCount` 用的是 `ThreadMXBean.findDeadlockedThreads()`，不是解析文本。
> 它同时覆盖 `synchronized` 监视器和 `ReentrantLock` 这类 ownable synchronizer。
>
> **踩过的坑**：jcmd 输出的是 `Found ONE Java-level deadlock`（英文单词），
> 不是 `Found 1 ...`，按数字写正则永远匹配不上，会一直报 0 —— 看起来像"没有死锁"，非常误导。

| 文件 | 内容 |
|---|---|

| `logs/app.log` | 应用日志，含完整 OOM 堆栈。10MB 轮转 |

### ★ 堆快照的三个反直觉行为（实测）

配了 `-XX:+HeapDumpOnOutOfMemoryError` 不代表"每次 OOM 都有快照"。实测结论：

#### ① 每个 JVM 进程只落一次盘

```
第 1 次 OOM（新 JVM） → java_pid1.hprof 生成，日志出现 "Dumping heap"
第 2 次 OOM            → 没有新文件，日志里 "Dumping heap" 计数仍是 1
第 3 次 OOM            → 同上
重启容器后再 OOM       → 又会落一次
```

HotSpot 内部用一个静态原子标记保证 OOM 报告**每个进程只做一次**
（`report_java_out_of_memory`），所以堆快照也就只有一份。

**实践含义**：想每次 OOM 都留证据，必须**每次重启 JVM**；
或者干脆用手动快照（下面第 ③ 点）。

#### ② 只有部分 OOM 类型会落盘

在**全新 JVM** 下逐类测试：

| OOM 类型 | 落盘 |
|---|---|
| 堆 `Java heap space` | ✅ |
| 元空间 `Metaspace` | ✅ |
| 直接内存 `Direct buffer memory` | ❌ **不落盘** |
| 线程数 `unable to create new native thread` | ❌ **不落盘** |

**实践含义**：排查直接内存 / 线程数 OOM 时，别指望 `dumps/` 里有东西。
这两个要看 `/status` 的 `directBuffer.usedMb` 和线程面板。

#### ③ 手动快照更小、更可控

| 快照来源 | 大小 |
|---|---|
| OOM 自动落盘（`java_pid1.hprof`） | **约 235MB** |
| 点「生成堆快照（live）」 | **约 31MB** |

差 7 倍的原因：`live` 会先做一次 Full GC，只保留存活对象；
OOM 自动落盘发生在堆**已经满了**的时刻，里面塞满了即将被回收的垃圾。

**要下载就用 live 快照** —— 31MB 稳当，235MB 风险高（见下）。

> ⚠️ 经 Cloudflare 下载时，**235MB 能不能过没有严格验证**。
> 已知确定的是：源站返回「空 body 的 4xx」会被 Cloudflare 显示成 `502 Host Error`。
> 大文件的真实上限见 [EXPOSE-VIA-TUNNEL.md](EXPOSE-VIA-TUNNEL.md) 的「已知限制」。
> 想稳就走 SSH 隧道（`./lab.sh ui` 有命令）。

## 5. ★ 最值得做的实验：两次快照对比

单次 dump 只能看到"现在有什么"，**两次对比才能看到"什么在涨"**。

```
1. 点「生成堆快照（live）」                → 基线，比如 heap-100.hprof
2. 点「渐进泄漏 +2MB×5」三次               → 制造差异
3. 再点「生成堆快照（live）」              → 样本，比如 heap-200.hprof
4. 两个 hprof 都下载，用 Eclipse MAT 打开
5. Histogram 对比 → 找实例数增长最多的类
6. 右键 → Merge Shortest Paths to GC Roots → 排除弱引用
```

**预期结果**：

```
LeakEntry 实例数：基线 = 0  →  样本 = 15
引用链：
  lab.jvm.support.LeakEntry
  ← ConcurrentHashMap$Node.val
  ← ConcurrentHashMap.table
  ← lab.jvm.support.LeakRegistry.STATIC_CACHE   ★ 就是这里
  ← (GC Root)
```

看到 `static` 字段 + `ConcurrentHashMap` + 只增不减 → 结论：
**缓存没有淘汰策略 / 没有 TTL**。这是生产环境第一大泄漏类型。

详细分析方法见 [DUMP-ANALYSIS.md](DUMP-ANALYSIS.md)。

## 7. 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面所有请求都失败 | 堆满了（刚做过 OOM 场景） | 点右上角**复位** |
| 曲线不动了 | 轮询失败 | 看顶部连接状态；堆满时先复位 |
| 复位后元空间没降 | 类卸载要等 Full GC | 等 1~2 秒再看 |
| 复位后死锁还在 | 死锁解不掉 | `./lab.sh restart` |
| 线程数一直很高 | 上次线程 OOM 的线程还在 sleep | 点复位（会 interrupt） |
| GC 空转点完没报错 | **正常**，G1 不抛这个错 | 看 GC 日志确认在空转 |
| 磁盘告警 | 堆快照 235MB/个 | `./lab.sh clean` |
