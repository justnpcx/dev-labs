Lighthouse 综合评分

打开问题版 → 打开优化版 →

怎么跑 Lighthouse

  1. 用 Chrome 打开问题版页面
  2. 按 F12 → 顶部标签栏找 Lighthouse （找不到就点 >> 展开）
  3. 勾选四个分类：Performance、Accessibility、 Best Practices、SEO
  4. Mode 选 Navigation，Device 选 Mobile（默认）
  5. 点 Analyze page load，等 15~40 秒
  6. 记下四个分数，然后对优化版跑一次，对比
预期：问题版 Performance 会很低（<50），优化版应该到 90+
具体分数取决于机器负载，以你实测为准 —— 但这个差距一定存在。
两个必须注意的前提
① 一定要用无痕窗口（Ctrl+Shift+N）。 你装的扩展会注入脚本、拖慢加载，分数会失真。
② 同一个页面多跑几次。Lighthouse 的分数有波动， 差 5~10 分是正常的，别拿单次结果下结论。
命令行也可以跑（更适合做 CI 门禁）：
npx lighthouse http://localhost:8082/lighthouse/audit/bad --view

这个场景和前面 14 个有什么不同

前面每个场景练的是一个技术点。Lighthouse 是综合评分 —— 它把几十项审计加权算成四个分数，正好当"整合测试"： 你在这里能一次看到前面学过的所有东西是怎么互相影响的。

为什么这两个页面没有侧边观察清单
观察清单本身会往页面里塞 DOM 节点、加文本、可能引入对比度问题 —— 那会污染 Lighthouse 的评分。所以这个场景的 bad/good 是干净的被测页面， 指南单独放在这一页。
页面右下角有个小浮层可以跳回来。

报告怎么读

Lighthouse 报告分三层，从上往下读：

层次看什么怎么用
分数 四个 0~100 的数字 只看趋势，别当 KPI。差 5 分没有意义
Metrics FCP / LCP / TBT / CLS / Speed Index
每个都有"实测值 + 分档"		 先看这个 —— 它告诉你哪里慢
Opportunities
+ Diagnostics		 具体审计条目，带"预计可省 XXX ms" 再看这个 —— 它告诉你为什么慢、怎么改
别被"预计可省 XXX ms"骗了
Lighthouse 的预估是单条独立测算的，不能简单相加。 它假设"其他都不变，只优化这一项"，所以把十条的预估值加起来， 会远远大于实际能省下的时间。
正确做法：按预估收益从大到小排序，一次改一个，改完再跑一次。

Lighthouse 的局限性

局限说明
实验室数据 是模拟环境跑出来的，不等于真实用户的体验。 真实数据要看 CrUX / RUM（真实用户监控）
只看首屏加载 不覆盖交互后的性能、长会话的内存增长
分数会波动 同一页面连跑三次可能差 10 分。要稳定就多跑取中位数
不测业务逻辑 它不知道你的接口该多快、你的图片该多大
最容易被误用的地方：把分数当 KPI
见过太多团队为了刷分做无意义的事（比如把首屏图片删掉、 把统计脚本延后到用户交互后加载）。
分数是手段，不是目的。真正要盯的是 Core Web Vitals 的 真实用户数据 —— LCP、INP、CLS 的 P75 分位值。
