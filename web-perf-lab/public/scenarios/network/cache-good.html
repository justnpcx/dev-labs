强缓存 + 协商缓存

← 回问题版

DevTools 观察清单

  1. Network 面板，不要勾 Disable cache
  2. 点「请求 3 次」，先看下面日志里的 transferSize
  3. 强缓存那组：第 2、3 次 transferSize=0 —— 请求根本没发出去
  4. 协商缓存那组：第 2、3 次 transferSize≈300 —— 发了，但只传了响应头
  5. 回 Network 面板核对：强缓存显示 (disk cache)； 协商缓存那条 Status 是 304
  6. 点 304 那条 → Headers → 看 Request Headers 里的 If-None-Match
预期对比（看 transferSize，不要看状态码）：
强缓存：第 2 次起 transferSize = 0
协商缓存：第 2 次起 transferSize ≈ 300（只有响应头）
⚠ 为什么日志里两组的「状态码」都是 200
fetch() 会把 304 透明处理掉 —— 它内部完成重验证， 然后把缓存里的 body 返回给你。所以 r.status 是 200、 body 也是完整的 920B。

光看状态码和 body，强缓存和协商缓存长得一模一样。 要区分只能看 transferSize（实际传了多少字节）， 或者去 Network 面板看原始的 304。

为什么这样分工

强缓存最快（零请求），但问题是"文件改了浏览器不知道"。 解决办法是文件名带内容 hash：app.a1b2c3.js —— 内容变了文件名就变，等于换了个 URL，缓存自然失效。

协商缓存每次都要问一趟，但保证拿到最新版。适合 HTML 这种 不能带 hash、又必须及时更新的入口文件。

ETag vs Last-Modified
ETag 是内容指纹（更强，精确到字节）；Last-Modified 是时间戳 （精度只有秒，而且"文件被碰了一下但内容没变"会导致误判）。 两个都给的话，浏览器优先用 ETag。
