强缓存 + 协商缓存

← 回问题版

DevTools 观察清单

  1. Network 面板，不要勾 Disable cache
  2. 点「请求 3 次」
  3. 强缓存那组：第 2、3 次 Status 应显示 200 (from disk cache) 或 (memory cache)，Size 列是 0 B
  4. 协商缓存那组：第 2、3 次 Status 是 304，Size 只有几百字节
  5. 点 304 那条 → Headers → 看 Request Headers 里的 If-None-Match
预期对比：
强缓存：transferSize = 0，请求根本没发出去
协商缓存：transferSize > 0（只有响应头），body 不传

两种缓存的分工

强缓存协商缓存
响应头 Cache-Control:
max-age=31536000		 Cache-Control: no-cache
+ ETag
有效期内容直接用本地副本向服务器确认
还发请求吗不发发，但只传头
状态码200 (from cache)304
适合带 hash 的静态资源HTML、常变的配置

为什么这样分工

强缓存最快（零请求），但问题是"文件改了浏览器不知道"。 解决办法是文件名带内容 hash：app.a1b2c3.js —— 内容变了文件名就变，等于换了个 URL，缓存自然失效。

协商缓存每次都要问一趟，但保证拿到最新版。适合 HTML 这种 不能带 hash、又必须及时更新的入口文件。

ETag vs Last-Modified
ETag 是内容指纹（更强，精确到字节）；Last-Modified 是时间戳 （精度只有秒，而且"文件被碰了一下但内容没变"会导致误判）。 两个都给的话，浏览器优先用 ETag。
