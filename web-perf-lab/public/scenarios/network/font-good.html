DevTools 观察清单

  1. 硬刷新 Ctrl+Shift+R，盯着虚线框
  2. 文字立刻就有（用的是系统字体），框不是空的
  3. 2.5 秒后字形会"跳"一下换成目标字体 —— 这就是 FOUT
  4. Network 里 /api/font 的 Initiator 应该是 preload
  5. 对比问题版：那边是 2.5 秒空白，这边是 0 秒空白
  6. 用 Performance 面板录一次，看有没有 Layout Shift 标记
预期：文字 0 秒可见
代价是字体到达时可能有一次轻微重排（FOUT）。
FOIT 和 FOUT 怎么选
FOIT（不可见）让用户看到空白，最糟的情况是"页面像坏了"。
FOUT（先 fallback 再换）让用户立刻能读，代价是一次重排。

绝大多数场景应该选 FOUT —— 能读的内容永远比好看的字形重要。

演示

刷新页面，注意文字是立刻出现、还是等了一会儿：

The quick brown fox jumps over the lazy dog
字体延迟 2500ms，但文字不等它

改了三处

<!-- ① head 里提前发现 -->
<link rel="preload" as="font" type="font/woff2"
      href="/api/font?..." crossorigin>

<!-- ② 别让文字等字体 -->
@font-face {
  font-display: swap;              /* 立刻用 fallback */

  /* ③ 把 fallback 的度量对齐真字体，减小换字时的重排 */
  size-adjust: 100%;
  ascent-override: 90%;
  descent-override: 22%;
}

为什么 crossorigin 不能漏

字体请求**永远是 CORS 模式**，即使同源。preload 时不写 crossorigin， 浏览器会用"无凭证模式"发一次、真正用字体时再发一次 —— Network 里出现两条一模一样的字体请求，等于 preload 白做了。
这个坑很隐蔽：功能完全正常，只是白下了一次。

再进一步：干脆不用 webfont

如果只是想要"好看的英文字"，用系统字体栈是零成本的： 

font-family: system-ui, -apple-system, "Segoe UI",
             Roboto, "Helvetica Neue", sans-serif;

零下载、零 FOIT、零 FOUT、零 CLS。代价是各平台字形不同 —— 对正文来说这几乎总是划算的。真要品牌字体，就只用于标题， 正文走系统栈。

自托管还是用第三方字体服务？
第三方字体域（Google Fonts 之类）要多一次 DNS + TCP + TLS 握手， 而且一旦对方慢，你的 LCP 就跟着慢。
自托管 + preload 通常更快也更可控， 代价是要自己管字体文件的版本和子集化。
