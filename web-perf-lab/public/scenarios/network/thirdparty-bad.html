DevTools 观察清单

  1. 硬刷新 —— 会先看到一段白屏，然后内容才一起出现
  2. Network 面板看那三条 /api/3p/tag.js，它们是串行的
  3. 看它们的 Initiator 是 document.write
  4. Performance 面板录一次，开启 Third parties 分组
  5. 看 Main 轨道：三段长任务都属于第三方，你一行代码都没写
  6. 看最下面「第三方总耗时」的数字
预期：三个脚本串行执行，共约 750ms 主线程占用
而且它们全都在首屏渲染之前 —— 用户看着白屏等它们跑完。
最要命的地方：这些代码不归你管
它们什么时候变慢、什么时候加了新逻辑、什么时候挂了 —— 你都不知道，也不会有 code review。

但它们的成本记在你的 Core Web Vitals 上。
Performance 面板的 Third parties 分组
录制结果里有一栏能把各来源的 CPU 时间、请求数、传输字节分开统计。
这是回答"我的页面为什么慢"最快的入口之一 —— 经常一开就发现大头全在几个你没想到的域名上。

问题出在这三行

// head 里，同步阻塞
document.write('<script src="//cdn.analytics.com/tag.js"></script>');
document.write('<script src="//cdn.chat.com/widget.js"></script>');
document.write('<script src="//cdn.abtest.com/sdk.js"></script>');

// 解析器必须：下载 → 执行 → 才能继续解析 HTML
// 三个串起来 = 三个脚本的时间相加

第三方脚本的四种代价

代价说明
阻塞解析同步脚本让首屏白屏
占主线程它们跑的时候你的事件、渲染都得排队
网络握手不同域名要重新 DNS + TCP + TLS
不可控对方改代码、挂了、变慢，你都只能被动接受

前三个你还能管，第四个是根本问题 —— 所以策略的重点是「限制它们能造成多大伤害」，而不是"让它们变快"。
