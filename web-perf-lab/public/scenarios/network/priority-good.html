DevTools 观察清单

  1. Network + Disable cache，勾上 Priority 列
  2. 硬刷新，找到 /api/image
  3. Priority 应该是 High，Start time 明显提前
  4. 看 Initiator 列 —— 这次是 preload，不是 HTML 解析
  5. 对比问题版：同样的图、同样的服务端延迟，LCP 差了多少
预期：Priority = High，LCP 提前到 1s 左右
服务端一个字没改，只是告诉浏览器"这张图很重要"。
preload 不是越多越好
每个 preload 都是一次"插队"。全站 preload 十几张图， 等于谁都没插队，还白白多了一堆提前发起的请求。
只 preload LCP 那一张。

演示

同一张图、同样的服务端延迟，唯一区别是 head 里多了一行 preload， img 上多了 fetchpriority="high"，去掉了 loading="lazy"。

改了三处

<!-- ① head 里提前声明，浏览器解析 HTML 时就开始下载 -->
<link rel="preload" as="image" href="/api/image?...">

<!-- ② 去掉 lazy，让浏览器按默认的 High 处理 -->
<!-- ③ 再显式提权，防止被同页其他资源挤下去 -->
<img src="/api/image?..." fetchpriority="high">

三个提示手段的区别

手段解决什么
preload发现晚 —— 资源藏在 CSS/JS 里，HTML 解析器看不见
fetchpriority排序错 —— 发现得不晚，但被排在了不重要的请求后面
preconnect连接贵 —— 第三方域要 DNS + TCP + TLS，提前握手

这张图是同源的，所以 preconnect 帮不上忙。 真实项目里 LCP 图常挂在 CDN 或对象存储上 —— 那时候 preconnect 才是大头。

字体是同一个道理

@font-face 里的字体浏览器发现得更晚（要先下载完 CSS 才知道有它）。 所以字体通常要 <link rel="preload" as="font" crossorigin>。
注意 crossorigin 是必须的 —— 字体请求永远是 CORS 模式，漏了会重复下载一次。 见 字体加载 场景。
