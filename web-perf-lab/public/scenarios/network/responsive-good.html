让浏览器自己挑

← 回问题版

DevTools 观察清单

  1. Network + Disable cache，硬刷新
  2. 看 /api/image 请求的 URL —— 里面的 w= 不是 1600
  3. 对比问题版的 Size 列，看省了多少
  4. Elements 选中 <img>，Console 里敲 $0.currentSrc —— 这是浏览器实际选中的那张
  5. 把窗口拖窄再刷新：下载的 w= 跟着变小
  6. 用 DevTools 的设备工具栏切到 DPR 3 的机型再刷新 —— 又变大了
预期：桌面 DPR 1 下下载 800w（1056 KB），窗口拖到 375px 且 DPR 1 时降到 400w（264 KB）
同一张图，不同设备拿到的字节数自动不同 —— 而问题版永远是 1600w / 4221 KB。
格式那一半，本场景演示不了
真实项目里响应式图片还有另一半：用 <picture> 优先发 WebP / AVIF，不支持再退回 PNG/JPEG —— 通常还能再省 30~60%。

但这个演练场零依赖，Node 内置没有 WebP/AVIF 编码器，造不出真文件。 我不想拿一个改了 Content-Type 的 PNG 来假装 —— 那样省下的字节是假的， 解码还会失败。
所以这一半只给用法，体积收益请以你项目里的实测为准。

改动就是这三个属性

<img
  src="/hero-800.png"
  srcset="/hero-400.png   400w,
          /hero-800.png   800w,
          /hero-1600.png 1600w"
  sizes="(max-width: 600px) 100vw, 800px"
  width="1600" height="900">

浏览器是怎么选的（本机实测）

视口DPRsizes 算出三档密度选中下载

375px2375px1.07 / 2.13 / 4.27800w1056 KB
375px3375px1.07 / 2.13 / 4.27800w1056 KB
1280px1800px0.50 / 1.00 / 2.00800w1056 KB
1280px2800px0.50 / 1.00 / 2.001600w4221 KB
1280px3800px0.50 / 1.00 / 2.001600w4221 KB
实测发现：Chrome 选的是「密度最接近 DPR」那一档
不是"不小于 DPR 的最小档"（规范里读起来像后者）。
看第三行：375px + DPR 3 时，密度 2.13 离 3 差 0.87， 而 4.27 差 1.27 —— Chrome 选了更接近但偏小的 800w。

这是实现选择（更省流量），别照着自己推的规则去预期浏览器行为。 不同浏览器、不同版本都可能不一样 —— 想确认就看 $0.currentSrc。

格式：用法在这里，收益请自己实测

<picture>
  <source type="image/avif" srcset="/hero-800.avif 800w, ..." sizes="...">
  <source type="image/webp" srcset="/hero-800.webp 800w, ..." sizes="...">
  <img src="/hero-800.png" srcset="..." sizes="..." width="1600" height="900">
</picture>

<!-- 浏览器从上往下试，第一个能解码的就用。都不支持才落到 <img>。 -->

经验值（不是在本机测的，仅供参考）： WebP 比 JPEG 省 25~35%，AVIF 再省 20~30%，但编码更慢。 具体能省多少完全取决于图片内容 —— 照片类收益大，图标类收益小。

别忘了自动化
真实项目里不会手写这些 —— 用构建插件（vite-imagetools、 next/image、sharp 脚本）自动生成多档尺寸和格式， 再自动吐出正确的 srcset。
手写的 srcset 迟早会和实际文件对不上。
