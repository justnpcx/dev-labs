DevTools 观察清单

  1. Network 面板，勾 Disable cache
  2. 点「发起快速请求」—— 服务端立刻响应
  3. Timing 里 Waiting for server response 应该只有几毫秒
  4. 点「直接请求最终地址」—— Network 里只有 1 条记录，没有 302
  5. 和问题版对比：总耗时从 ~1600ms 降到 ~10ms
预期：TTFB ≈ 5ms（问题版 1500ms）
无重定向：1 次往返（问题版 4 次）

优化 TTFB 的常见手段

手段适用
加数据库索引慢 SQL 是最常见根因
加缓存（Redis / 内存）读多写少的数据
并行调下游串行调 3 个接口 → 改成并发
CDN 缓存静态页内容不常变
流式响应（SSR）先吐 HTML 头，边算边发

改动一：把处理时间降下来

// 问题版：硬等 1.5 秒
await new Promise(r => setTimeout(r, 1500));
res.json({ ok: true });

// 优化版：直接返回（真实场景里是命中缓存 / 走索引）

改动二：不要中间跳转

// 问题版：三层跳转
/api/chain?n=3   → 302 → /api/chain?n=2
                 → 302 → /api/chain?n=1
                 → 302 → /api/chain?n=0
                 → 200

// 优化版：直接指到终点
/api/chain?n=0   → 200

重定向在什么情况下值得留

场景要不要留
HTTP → HTTPS留（安全必须）
裸域 → www留一跳，别再多
旧 URL → 新 URL留（保外链和 SEO）
为了"代码整齐"加的跳转砍掉
怎么发现线上有重定向链
在 Network 面板顶部筛选框输入 status-code:3xx， 就能把所有重定向捞出来。生产环境建议用 RUM（真实用户监控） 按 TTFB 排序，找出最慢的那批接口 —— 通常前 5 个就占了大部分收益。
