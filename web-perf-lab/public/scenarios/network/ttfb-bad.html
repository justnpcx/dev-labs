慢 TTFB + 重定向链

看优化版 →

DevTools 观察清单

  1. Network 面板，勾 Disable cache
  2. 点「发起慢请求」—— 一个 1.5 秒延迟的接口
  3. 点它 → Timing 标签，展开 Waiting for server response（就是 TTFB）
  4. 看它占了总时长的多少
  5. 再点「发起重定向链」—— 看 Network 里出现 4 条记录
  6. 逐个看 Status：302 → 302 → 302 → 200
  7. 对比第一条和最后一条的 Start time，差了多少
预期：慢请求 TTFB ≈ 1500ms，而 Content Download 只有几毫秒
重定向链：4 次往返，每次都白等一个 RTT
Timing 面板怎么读
Queued / Stalled —— 排队和等待（可能是并发限制或等前一个请求）
DNS / Initial connection / SSL —— 建连开销，复用连接时为 0
Request sent —— 发出请求，通常 <1ms
Waiting (TTFB) —— 服务器处理时间，慢查询/慢接口都在这
Content Download —— 下载响应体，和响应体大小正相关

重定向为什么贵

每一次 302 都是一次完整的往返： 客户端发请求 → 服务器回 302 → 客户端再发请求。 哪怕每个 RTT 只有 50ms，3 跳就是 150ms 的纯浪费， 而且这期间什么都干不了。

更糟的是：重定向还可能断掉连接复用， 如果跳到不同域名，还要重新 DNS + TCP + TLS。

别把 TTFB 和"网络慢"混为一谈
用户抱怨"网站慢"时，先看 Timing 拆解：
· 如果 TTFB 占大头 → 服务端问题，前端优化没用
· 如果 Content Download 占大头 → 响应体太大，去压缩/裁剪
· 如果 Stalled 占大头 → 并发排队，去合并/拆域名
定位错方向，后面全白做。
