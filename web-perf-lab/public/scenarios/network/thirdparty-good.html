DevTools 观察清单

  1. 硬刷新 —— 内容立刻就在，没有白屏
  2. Network 面板：三个 /api/3p/tag.js 出现在文档之后
  3. 看它们是不是并行下载的（不是串行）
  4. 看 preconnect 的握手有没有提前发生（Connection 列）
  5. Console 里会有一条第三方挂掉的提示 —— 但页面完全不受影响
  6. 看「第三方总耗时」：数字没变，但首屏可见时间提前了很多
预期：首屏 约 90ms 可见（问题版是 890ms 之后）
三个主要脚本的总 CPU 时间一样是 750ms —— 只是挪到了首屏之后。
第四个脚本会返回 500，用来演示 onerror 兜底。
⚠ 关键认知：这只解决了"白屏"，没解决"卡"
主线程该占还是占，只是从"渲染前"挪到了"渲染后"。
如果你在第三方跑的时候点按钮，照样会卡 —— 那属于 INP 问题。

要真正降低主线程占用，只有两条路： 少加载（砍掉不用的），或者隔离（塞进 iframe / Worker）。

改动：从"堵在 head"变成"首屏后注入"

// ① head 里只留一个 preconnect，不加载任何第三方代码
<link rel="preconnect" href="//cdn.analytics.com" crossorigin>

// ② 首屏渲染完之后，再动态注入
function loadThirdParties() {
  ['analytics', 'chat-widget', 'ab-test'].forEach((name) => {
    const s = document.createElement('script');
    s.src = `//cdn.../${name}.js`;
    // ★ 动态插入的 script 默认就是 async —— 并行下载，不阻塞解析
    // ③ 兜底：第三方挂了不能让页面跟着挂
    s.onerror = () => console.warn(`[3P] ${name} 加载失败，已忽略`);
    document.head.appendChild(s);
  });
}
// 等首屏画完再注入
requestAnimationFrame(() => requestAnimationFrame(loadThirdParties));

五个可用的手段

手段解决什么
preconnect握手开销（DNS + TCP + TLS）
动态注入 / defer阻塞解析 → 不阻塞
首屏后 / 交互后加载不跟首屏抢主线程
onerror 兜底第三方挂了不拖垮页面
iframe / Worker 隔离真正把主线程占用隔离出去
治本的办法是"少加载"
上线前对每个第三方问三个问题：
① 它带来了多少业务价值？② 能不能自研替代？ ③ 能不能只在需要它的页面/时机加载？

很多团队盘点完会发现，页面上挂着的七八个 SDK 里， 真正在用的只有两三个 —— 剩下的纯粹是历史遗留。
