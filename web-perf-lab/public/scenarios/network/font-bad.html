文字消失 2.5 秒

看优化版 →

DevTools 观察清单

  1. 硬刷新 Ctrl+Shift+R，盯着下面那个虚线框
  2. 框是空的 —— 文字在字体到达前完全不渲染，这就是 FOIT
  3. 约 2.5 秒后文字才出现
  4. Network 面板找 /api/font，看它的耗时和 Priority
  5. 看 Initiator 列 —— 是不是 CSS 里的 @font-face
  6. 对比优化版：同样的延迟，文字什么时候出现
预期：文字 2.5 秒不可见，然后一次性出现
在这 2.5 秒里用户看到的是一片空白 —— 他会以为页面坏了。
为什么字体总是"发现得很晚"
浏览器要先下载并解析 CSS，才知道有 @font-face， 然后才开始下载字体。这一串是串行的：
HTML → CSS → 发现字体 → 下载字体 → 文字可见

相比之下 <img> 在 HTML 解析时就被发现了。 这就是字体为什么特别需要 preload。
关于本演练场的字体载荷
服务端返回的是一个占位字节流，不是真字体（把几百 KB 二进制提交进仓库太脏， 构建期装字体又要依赖包管理器联网）。
但这不影响演示：FOIT 的时长取决于字体下载耗时， 不取决于下载完之后能不能解析成功。你看到的不可见期是真实的。

演示

刷新页面，注意文字出现的时刻：

The quick brown fox jumps over the lazy dog
字体延迟 2500ms

问题出在这一行

@font-face {
  font-family: 'LabFont';
  src: url('/api/font?delay=2500') format('woff2');
  font-display: block;      /* ← 字体没到，文字就不画 */
}

font-display 的五个值

值行为适合
auto由浏览器决定，通常等同 block不建议
block约 3s 不可见，然后 fallback图标字体
swap立刻用 fallback，字体到了再换正文
fallback约 100ms 不可见，然后 fallback折中
optional约 100ms 内没到就本次不用了极致性能

注意 swap 不是没代价 —— 它换来的是 CLS： 字体到了之后文字宽度会变，整段可能重排。所以还要配合 size-adjust / ascent-override 对齐 fallback 的度量。
