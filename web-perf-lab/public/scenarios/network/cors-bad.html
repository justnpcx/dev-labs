每次请求都触发预检

看优化版 →

DevTools 观察清单

  1. 用 http://localhost:8082 打开本页（见下方说明，本场景必须本地访问）
  2. 打开 Network，勾 Disable cache
  3. 点「发 3 次请求」
  4. 数一下 Network 里出现了几条记录 —— 应该是 6 条，不是 3 条
  5. 看 Method 列：每个业务请求前面都跟着一个 OPTIONS
  6. 点开 OPTIONS 那条 → Headers，看 Request Headers 里的 Access-Control-Request-Headers
  7. 看 Response Headers 里的 Access-Control-Max-Age
预期：6 次往返（3 × OPTIONS + 3 × GET）
每次业务请求都要先花一个 RTT 问"我能发吗"。
为什么会触发预检
只要请求满足下面任一条件，浏览器就必须先发 OPTIONS：
  • Method 不是 GET / HEAD / POST
  • 带了自定义请求头（如 X-Lab-Token）
  • Content-Type 不是这三种之一： text/plain、multipart/form-data、 application/x-www-form-urlencoded
问题版故意加了自定义头，所以每次都预检。
还有一个前提：必须跨源
同源请求根本不会有 CORS，自然也没有预检。
本页从 localhost 打 127.0.0.1 —— 同一台服务器、 同一个端口，但 host 不同就是两个 origin，所以预检真的会发生。

公网入口挂了 Cloudflare Access，而浏览器发预检时不带 Access 的 cookie， 请求会被 403 挡掉 —— 你在 Network 里看不到 OPTIONS。

然后打开 http://localhost:8082/network/cors/bad

这个请求为什么触发预检

// 问题版：带了自定义头 X-Lab-Token
fetch('http://127.0.0.1:8082/api/cors/preflight', {
  headers: { 'X-Lab-Token': 'abc123' }    // ← 就这一行导致预检
});

// 浏览器实际发出的：
// 1) OPTIONS /api/cors/preflight          ← 预检
//    Access-Control-Request-Headers: x-lab-token
// 2) GET /api/cors/preflight              ← 真正请求
//    X-Lab-Token: abc123

// 注意 URL 是绝对路径：页面在 localhost，请求打 127.0.0.1。
// host 不同 = 不同 origin，预检才会真的发生。

预检本身不是问题，重复预检才是

预检结果是可以缓存的 —— 靠响应头 Access-Control-Max-Age。 问题版的服务器把它设成了 0，所以每次都要重新预检。

生产环境一般设成 600（10 分钟）到 86400（1 天）。 注意：Chrome 对这个值有上限（目前 2 小时），设再大也没用。

什么时候该避免预检
高频接口（比如轮询、埋点）如果每次都预检，往返次数直接翻倍。 能改成简单请求就改 —— 但不要为了省一个 RTT 牺牲安全性。 该带鉴权头的还是得带。
