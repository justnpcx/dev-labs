DevTools 观察清单

  1. 硬刷新，盯着卡片上的「实验组 A/B」
  2. 它们一次都不会变 —— 服务端渲染的是什么就是什么
  3. Console 里没有任何 hydration 警告
  4. 看日志里「丢弃重建」的计数是 0
  5. Network 里看文档响应体，__SSR_PROPS__ 里多了 groups
  6. 对比问题版：那边几乎全部重建，这边一个都没有
预期：丢弃重建 0 张，无闪烁、无警告
服务端渲染的 DOM 被完整保留 —— SSR 的成果没有白费。
核心原则：客户端不要再算一遍
凡是服务端算过、且带不确定性的东西， 都序列化下去让客户端直接用。

框架里这个约定叫「同一份 state 决定同一份 UI」—— 服务端和客户端共享的是 state，不是"各自重新推导的过程"。

修复：把服务端的计算结果一起传下去

// server.js —— 服务端随机分组（这一步不变）
const groups = items.map(() => Math.random() < 0.5 ? 'A' : 'B');
html = items.map((p, i) => renderItem(p, groups[i])).join('');

// ★ 修复点：把 groups 一起序列化下去
const props = { items, groups };      // ← 客户端不用再猜

// 客户端 hydration —— 直接用，不重算
const group = props.groups[i];        // ★ 和服务端必然一致
if (node.outerHTML !== renderItem(p, group)) { ... }   // 永远不会进这个分支

两种正确做法

做法适用
序列化 state 下去
props.groups[i]		 服务端算出来的值客户端拿不到（随机数、请求头、数据库查询结果）
确定性重算
hash(userId + 实验名) % 100		 A/B 分组的标准做法 —— 两边独立算，结果必然相同，还不用传数据

真实项目里 A/B 分组**必须用确定性哈希**（通常按 user id）， 用 Math.random() 会导致同一个用户每次刷新分组都变 —— 那不只是 hydration mismatch，实验数据本身就是废的。

还有哪些地方容易踩
  • 格式化时间/数字时用了服务端和客户端不一致的时区或 locale
  • 渲染时读了 localStorage / window.innerWidth
  • 用 Date.now() 显示"X 分钟前"
  • 第三方库在初始化时注入随机 id（常见于图表库）
判断标准很简单：这段代码在服务端和客户端各跑一次，结果会一样吗？
