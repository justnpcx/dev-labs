核心思想：把"可交互"变成渐进的
用户只和眼前这一屏交互，那就先 hydration 眼前这一屏。

真实框架里的对应方案： React 18 selective hydration（按用户交互优先级）、 islands 架构（只 hydration 需要交互的岛屿）、 progressive hydration（分帧处理）。

改动：每处理一批就让出主线程

async function hydrateChunked(root, props, chunkSize = 1000) {
  for (let i = 0; i < root.children.length; i += chunkSize) {
    const end = Math.min(i + chunkSize, root.children.length);
    for (let j = i; j < end; j++) {
      hydrateNode(root.children[j], props.items[j]);   // 一批 500 个
    }
    await yieldToMain();      // ★ 把主线程还给浏览器
  }
}

// yieldToMain 优先用 scheduler.yield()，它让出后**优先**被调度回来，
// 不像 setTimeout(0) 那样排到队尾

问题版 vs 优化版

一次性分片
总 hydration 耗时约 240ms约 440ms（更长）
首屏可交互等 240ms约 20ms
期间能否滚动发涩顺滑
长任务一整块切成小段

注意总耗时反而变长了，这不是 bug：每次让出主线程，浏览器都会 趁机做一次渲染 —— 让出十几次就多付十几次渲染的代价。
分片优化的是「用户要等多久才能用」，不是"总耗时"。 这是响应性优化里最典型的一类交换：拿吞吐换延迟。

顺带一提：这页能跑这么快，靠的是一行 CSS
.pcard { content-visibility: auto } —— 视口外的卡片跳过布局和绘制。
没有它的话，8000 张卡片光是布局就要 2 秒以上， 而且每次让出都要重付一次，分片版会比一次性慢 9 倍 —— 本场景第一版就是这样，数据完全被带偏了。
但分片不是银弹
如果 hydration 总量是 5 秒，切成 100 片也只是把卡顿摊开， 用户滚到底部时那些按钮还是点不动。
真正的解法是少 hydration 一些东西： 静态内容根本不需要 hydration，只有要交互的部分才需要（islands 架构）。
