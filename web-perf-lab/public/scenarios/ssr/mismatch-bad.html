服务端和客户端算出了不同结果

DevTools 观察清单

  1. 硬刷新，盯着下面每张卡片上的「实验组 A/B」
  2. 它们会在 hydration 之后整片翻掉 —— 红边闪一下就是被重建的
  3. 打开 Console，看 hydration mismatch 的警告
  4. Elements 面板里选中一张卡片，勾上 Break on subtree modifications
  5. 刷新，会断在节点被替换的那一刻 —— 看调用栈
  6. 看日志里「丢弃重建」的计数：几乎全部
预期：约 一半以上的卡片被丢弃重建
服务端渲染的 HTML 被白白扔掉，浏览器还要重做一遍。
为什么会这样
服务端用 Math.random() 给每张卡片分了实验组， 客户端 hydration 时又调了一次 Math.random()。
两次结果当然不一样 —— 框架一比对就发现"服务端渲染的和客户端算的对不上"。

框架的处理方式很粗暴：丢掉服务端那棵子树，用客户端的结果重建。
这类 bug 的共同特征
服务端和客户端**跑了两遍**的东西，只要中间有不确定性，就会不一致：
Date.now() · Math.random() · localStorage · window · 时区 / locale 格式化

问题出在这里

// server.js —— 服务端随机分组
const groups = items.map(() => Math.random() < 0.5 ? 'A' : 'B');
html = items.map((p, i) => renderItem(p, groups[i])).join('');

// 序列化给客户端的 props 里**故意没带 groups**（bug 就在这）
const props = { items };        // ← groups 丢了

// 客户端 hydration —— 只能自己重算
const group = Math.random() < 0.5 ? 'A' : 'B';   // ★ 必然和服务端不同
if (node.outerHTML !== renderItem(p, group)) {
  node.replaceWith(rebuild(p, group));           // 服务端那棵树被丢掉
}

代价有多大

损失说明
SSR 白做服务端渲染的 DOM 被丢弃，那部分 CPU 全浪费
用户看到闪烁内容先按服务端的显示，然后整片变掉
hydration 更慢比对之外还要重建 + 重挂事件
极端情况整树重渲React 18 之前，mismatch 会导致整个根节点重新渲染

最坑的是：它不一定会报错。生产环境的 React 里 mismatch 常常只是静默地重渲， 你只看到"页面偶尔闪一下"，查半天查不出来。
