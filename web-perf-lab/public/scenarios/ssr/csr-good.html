DevTools 观察清单

  1. 硬刷新 Ctrl+Shift+R —— 内容立刻就在，没有白屏
  2. Network 里找 /ssr/csr/good 这条文档请求
  3. 点开 Response 标签 —— HTML 里已经带着商品列表
  4. 看它的 Size：比问题版的 HTML 大得多
  5. 对比 Performance 的 FCP / LCP —— 应该贴着 TTFB
  6. 注意没有 /api/ssr/products 这条请求了
预期：内容 随 HTML 一起到达，FCP ≈ TTFB
代价是 HTML 变大了，而且服务端多了一次渲染开销。
SSR 不是"免费变快"，是"把成本挪了个位置"
服务端要渲染（CPU 成本 + 可能的缓存需求）， HTML 变大（传输成本），客户端还要 hydration（下一个场景的主题）。

它换来的是：首屏可见时间、SEO、社交预览、弱网下的体感。 这笔账划不划算，取决于你的场景。
别被"SSR 更快"骗了
看 Load 事件的时间 —— SSR 版可能更晚， 因为它要传更多字节、还要跑 hydration。
SSR 优化的是用户什么时候看到内容，不是"页面什么时候加载完"。 这两个指标经常背离。

服务端做了什么

// server.js —— 同一份 render 函数，在服务端跑一遍
function ssrItemHtml(p) {
  return `<li class="pcard" data-id="${p.id}">...</li>`;
}

const items = ssrProducts(n);
html = template.replace('<!--SSR_MOUNT-->', items.map(ssrItemHtml).join(''));

// 再把数据序列化给客户端，免得它重新推导（推导就可能推歪 → mismatch）
html = template.replace('<!--SSR_PROPS-->',
  `window.__SSR_PROPS__ = ${JSON.stringify({ items })};`);

两版的关键差别

CSR（问题版）SSR（优化版）
HTML 内容空壳带全部内容
首屏可见等 JS + 数据随 HTML 到达
额外请求数据接口无
HTML 体积小大
服务端开销几乎为零每次渲染
下一步：hydration 的代价
页面现在"看起来好了"，但按钮还不能点 —— 事件还没挂上。 条目一多，这个"可见但不可交互"的窗口能有好几百毫秒。
