预期：滚一次触发 几十~上百次
优化版用 rAF 节流后，降到每帧最多一次（约 60 次/秒）
scroll / resize / mousemove / touchmove 是重灾区
这些事件触发频率远高于屏幕刷新率。以 mousemove 为例， 高性能鼠标能到 1000Hz —— 每秒 1000 次回调， 而屏幕只有 60Hz，你算 16 次，用户只看得到 1 次。
剩下 15 次纯属白烧 CPU，还抢占了本该用来渲染的时间。

每次 scroll 事件都会跑一遍"重活"：

· 遍历 200 个元素改样式

问题代码

// ❌ 每个 scroll 事件都直接干活
window.addEventListener('scroll', () => {
  const top = area.scrollTop;              // 读 → 触发布局

  for (let i = 0; i < items.length; i++) {
    items[i].style.transform = `translateY(${top * 0.1}px)`;  // 写 200 次
  }
  counter.textContent = ++count;           // 又写 DOM
});
// 滚动一秒 = 触发几十上百次 = 布局和样式计算被反复打断

为什么"每次事件都干活"是错的

浏览器渲染一帧的流程是： JS → Style → Layout → Paint → Composite， 一秒最多跑 60 次（60fps）。

而 scroll 事件可能一秒触发几百次。你在事件回调里做的事， 99% 的结果用户根本看不到（因为中间那些帧压根没被渲染）， 但它们确实消耗了 CPU，还让浏览器没法安心合成帧。

还有个更隐蔽的坑：被动事件
在 touchstart / touchmove / wheel 上加监听时，浏览器默认要等你的回调执行完才能决定要不要滚动 —— 因为你的代码里可能调了 preventDefault()。
如果你不打算阻止默认行为，加 { passive: true }， 浏览器就能立刻开始滚动，不等你。
