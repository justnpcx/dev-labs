录制的顶部会出现一条单独标注 Worker 的轨道 —— 重活跑到那儿去了。

这是 Worker 最直观的证据：同样的 CPU 时间，换了个人来扛。

改动：把重活挪出主线程

// 主线程只负责"发指令"和"收结果"
const worker = new Worker(workerUrl);
worker.onmessage = (e) => render(e.data);
button.onclick = () => worker.postMessage({ n: 36, times: 8 });

// Worker 里跑同样的代码，但它在**另一条线程**上
self.onmessage = (e) => {
  const { n, times } = e.data;
  let acc = 0;
  for (let i = 0; i < times; i++) acc += fib(n);
  self.postMessage(acc);
};

Worker 的四个硬约束

约束说明
没有 DOM碰不到 document，结果要 postMessage 回来
不能共享内存
（默认）		数据是结构化克隆过去的，大对象有拷贝成本
启动有开销几十毫秒。任务太短反而更慢，要衡量
是独立脚本要单独一个文件（或用 Blob URL 内联，本页就是）

拷贝成本是实际项目里最容易翻车的地方：传一个 50MB 的 ArrayBuffer 过去，克隆本身就能卡住主线程几百毫秒 —— 优化了个寂寞。
解法是用 Transferable 转移所有权（零拷贝）， 或用 SharedArrayBuffer 真正共享。

什么时候不值得上 Worker

任务只有 20ms 的话，Worker 的启动 + 消息往返可能就要 30ms， 还不如老老实实分片让出（见 交互延迟）。 经验线：单次超过 50ms 才值得考虑搬走。
