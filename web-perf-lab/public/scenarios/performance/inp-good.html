分片让出主线程

← 回问题版

DevTools 观察清单

  1. 打开 Performance 面板，点录制
  2. 连点「处理 1 条」3 次
  3. 停止录制
  4. 看 Main 轨道 —— 同样 700ms 的活，被切成 7 小段，段间有缝隙
  5. 看 Interactions 轨道，对比每条 duration
  6. 重点：总耗时几乎没变，但交互响应快了一个数量级
预期：交互 duration 从 700ms+ 降到 ~100ms 量级（= 单片的长度）
总计算量一样，INP 却降了一个数量级。
这不是"优化了计算"，是"优化了排队"
每一小段之间用 yield 把主线程还给浏览器， 浏览器就有机会插进去处理输入、渲染一帧。

代价是总时长可能略微变长（多了调度开销）—— 用一点吞吐换响应性，这个交换在 UI 上几乎总是划算的。

改动就多了个 yield

// 问题版：一口气跑完
heavyWork(700);

// 优化版：切成 7 片，片间让出主线程
for (let i = 0; i < 7; i++) {
  heavyWork(100);
  await yieldToMain();     // ← 把主线程还给浏览器
}

// 优先用 scheduler.yield()，它能让出后**优先**被调度回来，
// 不会像 setTimeout(0) 那样被排到队尾。
function yieldToMain() {
  if (typeof scheduler !== 'undefined' && scheduler.yield) {
    return scheduler.yield();
  }
  return new Promise((r) => setTimeout(r, 0));
}

三种让出方式怎么选

方式特点
scheduler.yield() 让出后优先被调度回来，不排队尾。Chrome 129+
setTimeout(0) 兼容性最好，但会被排到宏任务队尾，可能被别的任务插队
requestIdleCallback 只在空闲时跑，不保证及时执行 —— 不适合有 deadline 的活
更彻底的做法：干脆别放在主线程
如果这 700ms 是纯计算（不碰 DOM），扔进 Web Worker 才是终局方案 —— 主线程一点都不用让。
见 主线程卸载 那个场景。
