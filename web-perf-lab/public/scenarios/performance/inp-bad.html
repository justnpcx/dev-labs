DevTools 观察清单

  1. 打开 Performance 面板，点左上角录制
  2. 连点「处理 1 条」3 次
  3. 停止录制
  4. 看 Interactions 轨道 —— 每点一次出现一条
  5. 把鼠标放到每条上，看它的 duration
  6. 看 Main 轨道：那 700ms 是一整块红色长任务，中间没有空隙
预期：每条交互的 duration ≈ 700ms 以上
Interactions 轨道里那条就是 INP 的候选值。
为什么是 700ms 而不是 100ms
你点按钮的那一刻，主线程正在跑一个 700ms 的同步循环。 浏览器没法中断它 —— 你的点击事件只能排在队列里等着。

所以 INP 高不代表你的点击处理函数写得慢， 而是主线程太忙，没空处理输入。

问题出在这一行

button.onclick = () => {
  heavyWork(700);          // ← 同步跑满 700ms，主线程被独占
  render(result);
};

function heavyWork(ms) {
  const end = performance.now() + ms;
  let x = 0;
  while (performance.now() < end) x += Math.sqrt(x + 1);
  return x;
}

INP 到底量的是什么

阶段说明
输入延迟用户按下 → 事件回调开始执行
处理时长事件回调本身跑了多久
呈现延迟回调结束 → 下一帧画出来

INP 取这三段之和，并且是整次访问里最差的那一次（高分位）。 只优化平均值没用 —— 一次 800ms 的卡顿就能把 INP 拉到不合格。

生产里最常见的三个来源
  • 点击后同步做重计算 / 大数组排序 / 深拷贝
  • 输入框没做防抖，每次按键都触发全量重渲染
  • 第三方脚本（埋点、A/B、客服）占了主线程
它们的共同点是：都发生在主线程上，而主线程只有一个。
