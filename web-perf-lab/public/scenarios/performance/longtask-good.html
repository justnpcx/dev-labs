切片让出主线程

← 回问题版

DevTools 观察清单

  1. 同样的心跳计数器 —— 现在点按钮，它不会停，只是变慢一点
  2. Performance 面板录制，点「切片执行 800ms 工作量」
  3. 看 Main 轨道 —— 不再是一整块长任务，而是一串小片段，中间有间隙
  4. 每个片段都 <50ms，所以没有红色三角
  5. 对比两种写法的「实际耗时」—— 切片会略慢一点，但页面始终可交互
预期：计数器始终在跳，页面全程可点可滚
Main 轨道变成一串短任务，Long Task 数量降为 0
切片不是"更快"，是"更不卡"
总工作量一样，切片甚至因为调度开销会略慢。 换来的是：每一帧之间都留出了让浏览器处理输入和渲染的机会。
用户体验的差别远大于那点额外开销。

方案一：切片 + 让出主线程

async function runChunked(totalMs) {
  const deadline = Date.now() + totalMs;
  while (Date.now() < deadline) {
    const sliceEnd = performance.now() + 16;   // 每次只干 16ms（约一帧）
    while (performance.now() < sliceEnd) {
      x += Math.sqrt(x + 1);
    }
    // 把控制权交还给浏览器：处理输入、渲染、跑 rAF
    await new Promise(r => setTimeout(r, 0));
  }
}

关键就是那个 await setTimeout(0) —— 它把长任务切成一串短任务，任务之间浏览器有机会干别的。

方案二：Web Worker

// 主线程
const worker = new Worker('/assets/worker.js');
worker.postMessage({ ms: 800 });
worker.onmessage = e => console.log('结果', e.data);

// worker.js（跑在另一条线程，完全不碰主线程）
onmessage = e => {
  const deadline = Date.now() + e.data.ms;
  let x = 0;
  while (Date.now() < deadline) x += Math.sqrt(x + 1);
  postMessage(x);
};

Worker 是真正并行的 —— 主线程一点不受影响，连一次让步都不用。 代价是：不能直接操作 DOM，数据要通过 postMessage 传递（有序列化开销）。

怎么选

方案适合代价
切片 + 让出需要操作 DOM 的批处理总耗时略增
Web Worker纯计算（解析、加密、图像处理）不能碰 DOM
requestIdleCallback不紧急的后台任务时机不可控，可能不执行
拆成多次交互本来就能让用户分步完成改产品交互
